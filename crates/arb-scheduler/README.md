# Bounded research scheduling

This crate implements the ARB-013 admission and dispatch foundation. It does not start Tokio tasks, spawn CPU threads, publish metrics, or claim that production workers already use its queues. It accepts `arb-domain::NetworkId`; its generic generation token can carry `arb-control::WorkGeneration` unchanged.

The scheduler starts with both network gates closed. A control owner installs an acknowledged research generation with `set_gate(network, Some(generation))`. Ingestion calls `try_enqueue` with the observation's monotonic timestamp, stage and bounded correlation ID. Admission rejects a closed gate, old generation, future timestamp, expired observation or full network queue with a typed reason and returns the rejected payload to its caller.

Two FIFO queues partition pending work by network. Dispatch alternates between eligible networks and grants at most one permit per call. Limits reserve at least one global in-flight slot for the other network. A saturated Solana queue or outstanding Solana permit therefore cannot consume every Base execution slot. Queue capacity is capped at 65,536 items per network and global in-flight capacity at 256 permits; these are validation ceilings, not recommended operating values. Payload byte sizes must also be bounded by decoder/capture limits before admission; a count limit cannot bound arbitrary generic payload allocations.

A `WorkPermit` owns its in-flight quota until `finish` or drop. CPU algorithms inspect the permit's cancellation token between bounded chunks. `fence` signals running work and removes queued work; it never joins a CPU job. A cancelled thread may still be computing. `finish` rechecks generation, gate and original observation deadline and rejects its result when invalid. The durable control worker must **still** admit a successful result under its own lease/generation lock; scheduler success is neither durable acknowledgement nor execution authorization.

Queued payload destructors run after the scheduler lock is released. Do not execute arbitrary payload cleanup or external I/O on the control acknowledgement path. Lock scope contains only bounded queue/accounting operations. Stage snapshots copy fixed-cardinality aggregates for two networks × six stages, with queue age, queued/in-flight counts, acceptance, completion, and typed drop counters. Correlation IDs travel with work and are not metric labels. No dashboard/analytics network call happens under a scheduler lock.

For each stage, callers must map rejection to an explicit policy: ingestion/snapshot gaps require resynchronization; quotes and simulations may be discarded and recomputed from fresh state; persistence/control writes must use their own durable bounded path and must never be silently dropped. This generic scheduler must not be used to discard durable command, journal or reconciliation writes when full.

Integration remains explicit: install a fixed-size CPU pool, use Tokio for I/O, connect local control fencing before any durable stop acknowledgement, pass completed research results through `ControlWorker`, export stage metrics asynchronously, and record p50/p95/p99 on a named host. The crate intentionally does not invent latency or profitability measurements. Across separate chain processes, a supervisor must allocate each process a CPU/memory budget; the in-process global cap does not coordinate separate processes by itself.

Run `cargo test -p arb-scheduler`. Deterministic tests cover a 100-item overload into a three-item queue, FIFO/round-robin ordering, a blocked Solana permit with repeated Base dispatch, global quota and abandonment, admission/dispatch/completion staleness, restart with closed gates, generation rotation/ABA, and fencing before a CPU job can be released. The stop test proves ordering with a channel barrier; it is not a latency benchmark.
